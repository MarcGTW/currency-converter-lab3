# Технический план реализации · NASA NEO Tracker

- Документ: План архитектуры и реализации
- Целевой стек: Node.js 22+ (native `node:http`, `node:test`, `node:fs`), Vanilla ES6+ модули, чистый CSS без тяжелых фреймворков.

---

## 1. Архитектура системы

Приложение строится по модульной архитектуре с чётким разделением ответственности:

```
[ NASA NeoWs REST API ]
         ▲
         │ (HTTP GET)
         ▼
[ lib/neo.js (Server Proxy & Network Loader) ]
         ▲
         │ JSON /api/neo?date=YYYY-MM-DD
         ▼
[ server.js (Native HTTP server + Static File Server) ]
         ▲
         │ HTTP / JSON
         ▼
[ Browser Client ]
 ├── public/index.html    (Семантическая разметка GUI)
 ├── public/styles.css    (Космический дизайн, переменные, адаптив)
 ├── public/neo-core.js   (Бизнес-логика, разбор JSON NASA, расчёты, валидация)
 ├── public/neo-cache.js  (Управление кэшем localStorage, валидация схемы)
 └── public/neo-app.js    (Контроллер GUI, события, фильтры, рендер)
```

### 2.2. Контракт локального кэша `neo_cache_v1`
Объект снимка сохраняется в `localStorage` с проверкой схемы:
- `date`: строка `YYYY-MM-DD`
- `element_count`: целое неотрицательное число
- `asteroids`: массив объектов астероидов
- `source`: строка источника
- `cached_at`: дата и время сохранения

## 3. Модули и ответственность

1. **`lib/neo.js`**:
   - Формирование URL к NASA NeoWs API.
   - Поддержка `api_key=DEMO_KEY` и настраиваемого таймаута (6 секунд).
   - При сбое сети или тайм-ауте: выброс понятных типизированных ошибок на русском языке.
   - Если дата пустая (0 астероидов): возврат корректного снимка с `element_count: 0`.

2. **`public/neo-core.js`**:
   - `isValidNeoDate(dateStr)`: регулярное выражение + проверка дней в месяцах (28/29 в феврале, 30/31 в остальных).
   - `validateNeoDate(dateStr)`: проверка формата, диапазона `1900-01-01` .. будущее.
   - `parseNeoResponse(payload, targetDate)`: извлечение астероидов из `payload.near_earth_objects[targetDate]`, расчет диаметров, скоростей, дистанций.
   - `formatDistance(km, ld)`: форматирование с разделителями тысяч и переводом в лунные расстояния.
   - `formatSpeed(km_s, km_h)`: форматирование с разделителями тысяч.
   - `formatDiameter(min_m, max_m)`: отображение диапазона в метрах или километрах.
   - `filterAndSortAsteroids(list, filterType, sortBy)`: фильтрация по флагу опасности и сортировка.

3. **`public/neo-cache.js`**:
   - `saveNeoCache(snapshot)`: валидация схемы перед записью.
   - `loadNeoCache()`: безопасное чтение, обработка поврежденного JSON, возврат `null` при невалидности.
   - `clearNeoCache()`: удаление кэша.

4. **`public/neo-app.js`**:
   - Связывание DOM и бизнес-логики.
   - Анимированный счетчик объектов и бейджи тревоги для опасных астероидов.
   - Модальное/инлайн уведомление с кнопкой «Использовать данные из кэша (ДД.ММ.ГГГГ)».

5. **`server.js`**:
   - Поддержка `/api/neo` с валидацией входного параметра `date`.
   - Обновление CSP для разрешения доступа к ресурсам.

## 4. План тестирования

1. Тестирование валидации дат:
   - Корректные даты (текущая, прошлые, високосный год 2024-02-29).
   - Некорректные даты: невисокосный 2023-02-29, 2026-02-31, 2026-04-31, пустая строка, спецсимволы.
2. Тестирование парсера JSON NASA:
   - Корректный ответ с несколькими объектами (опасными и неопасными).
   - Ответ с нулевым количеством астероидов (`element_count: 0`).
   - Поврежденный или неполный JSON.
3. Тестирование форматирования:
   - Округление и разделители для дистанции и скорости.
   - Переключение метров в километры для диаметров > 1000м.
4. Тестирование кэширования:
   - Сохранение и считывание корректного снимка.
   - Игнорирование поврежденного кэша.
5. Тестирование API-роута сервера `/api/neo`:
   - 200 OK при валидной дате и мок-загрузчике.
   - 400 Bad Request при невалидной дате.
   - 502 Bad Gateway при сбое источника.
